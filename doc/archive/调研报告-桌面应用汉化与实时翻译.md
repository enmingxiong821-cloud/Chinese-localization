## 一、结论先行

1. **这个赛道已经有成熟且分工明确的开源生态**：针对 Claude Desktop 的汉化项目星标最高已到 7.6k，通用 Electron 汉化器、VS Code 系语言包、游戏/视觉小说实时机翻、屏幕 OCR 覆盖层各有代表作。**不存在"没人做过"的机会，但存在"没人做对"的机会。**
2. **"汉化"不是一个技术，是六个技术**（见第二节技术谱系）。社区项目基本都只吃其中一到两种，且大量把版本适配、术语一致性、覆盖率验收写死在脚本里。
3. **VS Code 系（Cursor / Windsurf / Trae / Copilot）根本不该用"补丁"思路**。它们有完整的官方 i18n 机制（`nls.keys.json` + `nls.messages.json` + 语言包扩展 + `argv.json` 的 `locale`）。正确做法是**语言包合成器**：官方译文（microsoft/vscode-loc）打底 + 补齐该 fork 私有键的译文，产出一个完整 `.vsix`。零风险、不破签名、随更新存活。
4. **Claude Desktop 存在"轻量汉化"路径**：它其实自带 i18n 资源体系（`resources/en-US.json`、`ion-dist/i18n/*.json`、`ion-dist/i18n/statsig/*.json`）+ 前端语言白名单 + `config.json` 的 `locale`。只注入中文资源 + 白名单 + locale **不需要改 `app.asar`**，也就不需要重签名 / 破坏完整性哈希，还能保住 Cowork 沙箱。只有少数硬编码文案才需要 chunk 替换或运行时 DOM 修复。
5. **运行时注入是被严重低估的方案**。`pen-dev-i18n` 用 CDP + Node inspector 在内存里做替换，一个字节都不写盘，秒级回滚、随更新存活、还能热切换语言。代价只是需要以调试端口启动（用一个启动器封装即可）。
6. **"专业"与"机翻脚本"的分水岭在工程细节不在模型**：术语表、翻译记忆、占位符保护、长度约束、上下文区分译法、不译清单（品牌/快捷键/单位/路径）、版本指纹与 fixture 回归、覆盖率门禁。目前没有一个开源项目把这些做全。
7. **实时翻译是与汉化正交的第二条产品线**，可以复用同一套"翻译引擎层"（术语表 + TM + 多引擎适配），但 UI 层完全不同（分层透明置顶窗口 vs 进程内注入）。

## 二、技术谱系（按侵入性从低到高）

| 层级 | 手段 | 原理 | 优点 | 缺点 | 代表实现 |
|---|---|---|---|---|---|
| **T0** | 应用自带 i18n 开关 | 应用本身就内置了多语言，只是没暴露入口 | 零风险、官方支持、随更新存活 | 覆盖率取决于官方；开关可能未文档化 | Codex Desktop 的 `enable_i18n`；VS Code 系 `argv.json` 的 `locale` |
| **T1** | 语言包扩展 | 生成/安装贡献 `contributes.localizations` 的扩展，提供 `translations/*.i18n.json`（键→译文） | 零侵入、官方机制、可增量、可随更新存活 | 只适用于 VS Code 系（Electron 但走自有 i18n） | `polang233/cursor-language-pack`、`microsoft/vscode-loc` |
| **T2** | 运行时注入（不改盘上文件） | 以 `--remote-debugging-port` 启动 → CDP 注入 DOM 翻译层；以 Node inspector 挂主进程钩子改原生菜单 | 不破签名、可秒级回滚、随更新存活、可热切语言 | 需要调试端口启动；canvas 绘制文本、系统文件对话框覆盖不到 | `wh000wh000/pen-dev-i18n`（1880 词条，`~/Pen汉化` 启动器） |
| **T3** | 资源替换（i18n JSON） | 把中文语言资源写进应用的资源目录 + 修补前端语言白名单 + 写 `locale` 配置 | 效果彻底、原生渲染、不依赖调试端口、不需要运行时开销 | 应用更新后需重打；需备份/还原；WindowsApps/MSIX 目录需管理员权限 | `javaht/claude-desktop-zh-cn`、`Jyy1529/claude-desktop_win-zh_cn` |
| **T4** | asar 解包/注入/重打包 | 备份 `app.asar` → 解包 → 注入 preload/主进程钩子 → 重新打包 | 能拦远端语言包响应、能改主进程菜单；对"语言包从 CDN 拉"的应用唯一解 | macOS 有 `ElectronAsarIntegrity` 校验，必须重签名；Windows 改 exe 内嵌哈希会破 Authenticode，Cowork 等沙箱可能拒启 | `hlmd/postman-chinese-injector`、`qqxpee/antigravity2-cn` |
| **T5** | 屏幕 OCR + 覆盖层实时翻译 | 截图 → OCR → MT → 分层透明置顶窗口按坐标覆盖译文 | 与目标应用完全解耦，任何软件（含游戏/视频/PDF）都能用 | 版面还原难、延迟/抖动、无法处理可交互控件文本 | `ramjke/Translumo`、`OneMoreGres/ScreenTranslator`、`Hon-Lu/OverTranslate` |
| **T6** | 音频 ASR + MT + 字幕层 | WASAPI loopback 抓系统音 → faster-whisper → MT → 悬浮双语字幕 | 覆盖会议/直播/视频等无字幕场景 | 延迟更高、需要音频回环权限 | `Varyoo/realtime-subtitle`、`RexBearIU/bilingual-subtitle-app`、`fly3366/NepNep` |

### 混合策略（社区实际最优形态）

真实项目几乎都是混合，典型组合：

- **T3 + T4**（Claude Desktop）：注入 i18n JSON + 白名单 + locale → 剩余硬编码文案用 chunk 等长替换 → 极少数仍漏的用运行时 DOM 修复兜底。
- **T2 + T4**：默认走运行时注入（不写盘），给"必须彻底"的场景提供 asar 静态补丁作为可选项。
- **T1 + T2**（VS Code 系）：语言包覆盖 99.8% 官方键，fork 私有键（Cursor 的 Agent 面板、设置页）用语言包补，剩余硬编码用运行时兜底。

## 四、可直接复用的组件清单

**注入与打包**

- `@electron/asar`（asar 解包/打包，Node）；`npx` 回退方案见 postman 项目
- Node 内置 `WebSocket`（Node ≥ 22）→ **零依赖 CDP 客户端**，不需要 `chrome-remote-interface` 之外的库
- Electron preload 注入点：`app.asar` 内 `preload_desktop.js` / `preload/*/index.js`；未打包形态直接改 `resources/app/`

**OCR（屏幕取词）**

- **Windows 首选**：OneOCR（Windows 11 截图工具内置，零依赖零模型）→ 见 `b1tg/win11-oneocr`、`game-translator-lens`
- **跨平台首选**：RapidOCR（ONNX Runtime，pip 即用）或 `RapidOCR-json`（进程外 CLI + JSON）
- **零依赖兜底**：`Windows.Media.Ocr`（WinRT，系统自带）
- **备选**：PaddleOCR PP-OCRv5、Umi-OCR（批量/离线工程化最全）、Tesseract（最老但最杂食）

**翻译引擎**

- **本地离线**：Argos Translate（CTranslate2 + 模型包）、Hunyuan-MT / Qwen-MT / NLLB-200 / OPUS-MT（自托管）、Mozilla Bergamot（浏览器级本地翻译）
- **云端**：DeepL、Google、微软、有道、百度、腾讯、火山，以及任何 OpenAI 兼容端点（含 DeepSeek / GLM / Kimi / Qwen）

**音频（可选 T6）**

- WASAPI loopback（Windows 系统音回环）→ `faster-whisper` / `whisper.cpp` → MT → 悬浮字幕

## 五、关键工程洞察（决定"专业"与"能跑"的差距）

### 1. 版本适配必须数据驱动，不能写死在脚本里

每个应用升级后，资源目录结构、键集合、chunk 文件名都会变。社区项目普遍靠"打补丁脚本 + 报错让人提 issue"。专业做法：

- 每个受支持的应用版本存一份**资源指纹**（文件清单 + 尺寸 + hash + i18n 键集合 + 关键 DOM 锚点）
- 启动时校验指纹：匹配 → 直接用；不匹配 → **明确报"需要适配"，绝不静默漏翻/错翻**
- 每个适配规则配 fixture 回归测试，CI 门禁

### 2. 翻译质量工程 = 差异化护城河

| 机制 | 解决什么问题 | 参考 |
|---|---|---|
| 术语表（glossary） | 同一术语在不同界面译法不一致 | `KeywordGacha` 自动生成 |
| 翻译记忆（TM，key→译文 + 模糊匹配） | 应用升级后新增/改动少量键，不必全量重译、也不重复调用 API | postman 的"译文热更新"数据分支 |
| 占位符保护 | `{count}`、`{{name}}`、`%s`、`%1$s`、`\n`、`<b>` 被模型改坏导致崩溃/渲染错乱 | 各家汉化项目都踩过 |
| 不译清单 | 品牌名、快捷键、单位、路径、断言/枚举值 | Jyy1529 明确记录"翻 `label` 会丢图标" |
| 长度约束 | 按钮/菜单/标签译文过长导致布局崩坏 | — |
| 上下文区分 | 同一英文词在按钮/菜单/提示里译法不同 | pen-dev-i18n 用 key 路径做上下文 |
| 占位/模糊清单 | `{size} MB`、`Ctrl+Enter`、`Windows (x64)` 这类不该翻的 | Jyy1529 的 `I18N-COVERAGE-REPORT.md` |

### 3. "内部标识"与"可见文本"必须分离（血泪教训）

Electron 前端里，同一个字符串可能同时是：
（a）JS 内部枚举/`label`/图标名 → 翻了会逻辑错乱（丢图标、路由失效）
（b）DOM 可见文本 → 该翻

**规则**：静态补丁只翻"确定是可见文本"的位置；拿不准的一律交给运行时 DOM 替换（只改渲染结果，不动数据）。

### 4. AI 化闭环（已被验证的最佳工作流）

```
extract  →  抓取源语言键表 + 当前界面实际文案
todo     →  输出未翻译清单（含上下文/截图锚点），交付给人或 LLM
translate→  带术语表 + 上下文 + 占位符保护的批量翻译（本地或云端）
merge    →  合并进词典（内置占位符/长度/重复校验）
verify   →  覆盖率 + 回归，未达标退出码非零
```

`pen-dev-i18n` 的 `--json` 全命令契约（给 AI agent 用）值得直接照抄。

### 5. 不要一上来就改用户的安装包

改动用户已装应用是**破坏性操作**（签名、完整性校验、沙箱、更新流程）。专业工具应：

- 默认只做只读扫描（`scan`/`status`/`coverage`）
- 任何写操作前强制备份 + 生成还原脚本
- 明确区分"轻量模式（只写资源 JSON，不碰 asar/exe）"与"完整模式（改 asar/签名）"，把风险讲清楚
- 优先选可回滚的方式（运行时注入 > 资源注入 > asar 重打包 > 改可执行文件哈希）

调研中多个项目（如 postman-chinese-injector）的免责声明具参考价值，务实的边界是：

- **不分发**目标应用的源码、二进制、原始语言包 —— 只发布工具与你自己创作的译文
- 译文派生自目标应用的界面字符串，**不要主张版权**，权利人提出异议即配合下架
- 明确"非官方、无关联、未获授权"；工具只修改**用户自己机器上自己安装**的应用
- 提醒用户遵守目标应用的服务条款 / EULA（可能含禁止反向工程、修改、衍生作品的条款）
- 企业受管设备上绕过组织策略存在合规风险，应提示
